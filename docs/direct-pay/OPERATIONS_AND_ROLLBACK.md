# Operations and rollback

First release: validate schema in disposable DB -> deploy compatible code with new orders disabled -> mount isolated configuration -> validate callbacks/worker -> allowlist -> operator-authorized external tests -> review acceptance evidence. Never publish an unverified binary or assume the development HEAD is deployed.

Rollback: reliably persist directpay.create_enabled=false and verify it; retain callbacks, Inbox, original account revisions and query/cache reconciliation. A write failure returns 503, not success. Retain all additive tables and users.direct_pay_credit_total. Never restore an older full DB snapshot to undo code, never DROP payment tables, and never share a Redis namespace with a pure-upstream hydrator after direct credits exist. On first release prefer stop-new-orders and forward repair. Only use a specifically verified compatible payment binary; the local public-key rollback fixture is not blanket approval for certificate-mode or production rollback.

Inspect pending/quarantined direct_pay_events, review_required direct_pay_orders, earliest next_query_at and unknown/paid-uncredited age. Fixed warning categories signal Inbox retry, query persistence or cache reconciliation. Local 40-callback latency is recorded, but sustained-load p99 and operational metrics/alert integration remain unvalidated.

Evidence mismatch: preserve event, compare immutable identity/amount with authenticated provider query and official merchant records. Never edit quota or bypass ledger uniqueness. Wallet capacity/deleted user: preserve payment proof and investigate; no automatic refund is issued. Missing revision: restore the exact authorized historical configuration, never repoint old orders to another merchant. Operator refunds require a separately approved process and quota disposition; P7 is not implemented.

Daily statement comparison is a manual operator procedure using merchant transaction IDs vs ledger/order snapshots; polling is not bank reconciliation. No production SQL commands are supplied. Local full-program fixture-image rollback has now passed; see LOCAL_REHEARSAL.md. Production remains unauthorized/unknown.

Production new-order enablement is hard-blocked pending repair of the inherited batch/cache-loss overspend demonstrated in LOCAL_REHEARSAL.md. Do not remove the gate based on payment-only tests.

## Wallet synchronous persistence cutover — 2026-10-03

The approved candidate no longer batches user wallet money. Do not perform a rolling mixed-version wallet deployment. These are operator prerequisites, not actions executed against production:

1. Keep direct-pay production creation disabled. Stop new relay/task admissions on **every** old writer node; drain in-flight requests, task settlement/refunds and admin wallet mutations. Keep historical payment callbacks/settlement available through a compatible isolated payment worker as needed.
2. Let each old process flush its process-local batch queues successfully while DB is reachable. Check errors and reconcile balance/usage evidence; a `batch update finished` log alone does not prove all SQL writes succeeded. Old failed batches are not automatically requeued. If queue emptiness/success cannot be established, stop cutover and reconcile; do not kill old processes or infer safety from waiting one interval. There is no new durable journal or drain-admin endpoint in this bounded patch.
3. Snapshot/reconcile after draining, stop all old wallet writers, then start only compatible synchronous-wallet nodes. Remove stale user quota caches only under the approved operational runbook; never reset live balances from an old snapshot. Token/stat batching can remain enabled. Reopen relay admissions only after SQL capacity/error checks and accounting checks pass. This document does not authorize production operations.
4. Rollback must retain the wallet synchronous fix, direct-pay schema/readers, final provider certificate verification and historical notification/settlement workers. Disable new orders and drain consumers first. The earlier public-key payment-only rollback rehearsal predates this wallet change and is **not** a safe whole-site rollback target. Do not resume older batch-wallet writers; a rollback build must carry this fix, or consumption must remain stopped pending reconciliation.

Load/availability impact: wallet pre-reserve and each nonzero settle/refund now add an immediate user-row SQL update (typically reserve + one delta per completed call), replacing per-user/per-interval coalescing. Refund/settle cache invalidation also adds synchronous Redis DEL and later hydration SELECT. Hot-user row contention, DB pool wait, commit latency, timeouts and DB availability now directly affect admission/settlement. Measure representative concurrency and hot-account distributions, error rate, pool saturation and p95/p99 before production. Local functional concurrency tests are not load acceptance. Do not restore wallet batching as an overload fallback; rate-limit admissions/capacity-plan while retaining SQL authority. SQL ambiguous commits require reconciliation, not blind retry of non-idempotent refunds.
